# Decisions

1. **Indexes.** `employees` gets a unique `emp_code` index (identity), a compound `(department, joined_on)` index for the headcount queries in `department_summary` and `department_trend`, and a standalone `joined_on` index for the trend's per-day headcount lookup. `attendance_logs` gets the unique `(emp_code, date)` natural key, a `(date desc, emp_code asc)` index that backs the required `list_attendance` sort, a `(status, date)` index that lets the analytics `$match` on status+date use an index, and an `(emp_code, punch_in desc)` index that lets `punch_out` find the most recent open record across midnight in one indexed lookup. No standalone `status` index is needed because the analytics always filter on date too.

2. **Punch-in race.** Both requests compute the attendance date (R1) and the late minutes (R2), then attempt an `insert_one`. The unique `(emp_code, date)` index lets exactly one insert win; the other gets `DuplicateKeyError` and is converted to 409. There is no check-then-insert; the index is the lock. Punch-out uses the same trick: `find_one_and_update` with `punch_out: null` in the filter is atomic, so the second concurrent punch-out gets `None` and is converted to 409. Regularize uses `find_one_and_update` with an `$expr` guard on the original `history` length, so a concurrent edit that appended in the meantime no longer matches the filter and the loser gets 409 — no silent history loss.

3. **Ties.** Standard competition ranking (`1, 2, 2, 4`): rows are sorted by `total_late_minutes` desc then `emp_code` asc, the rank advances to the array index when the total changes, and `limit` is applied *after* ranking — every row whose `rank <= limit` is returned. So if `limit=2` and the top three are `95, 95, 35`, the response has rank-1, rank-1 and rank-3 (no rank-2).

4. **Headcount.** `department_summary` starts from `employees` filtered to `joined_on <= last day of month`, then `$lookup`s their `attendance_logs` with the month filter inside the sub-pipeline. Group is by `department`, with `headcount: {$sum: 1}` — so an employee with zero logs still contributes 1 to headcount (the lookup yields an empty `logs` array but the document itself is still in the group). `department_trend` does the per-day headcount via a `$lookup` of `employees` filtered to `joined_on <= $_date`, so people who join mid-range start contributing from their join date.

5. **At 100x.** I would profile the indexed aggregation plans with `explain` first; the moving-average `$setWindowFields` and the per-row `$lookup` on `department_trend` are the most likely hot spots. Then I'd consider daily/monthly rollups (one summary document per `(emp_code, date)` or `(department, date)` written at punch-out / regularize time) and have the analytics read from the rollups, keeping `attendance_logs` as the immutable audit source. The per-row headcount `$lookup` could be replaced by a single upfront fetch of the department's roster and a `$set` with `$size`+`$filter`, removing N lookups in favour of one. The leaderboard would benefit from a `(emp_code, date)` covering index for the month match.
