# Starter review

This file is the write-up of the review of the starter `app/main.py`. The starter runs and the happy path works, but it has more than ten defects across the helpers and the endpoints. Each defect is listed with a concrete failing input, and the fix that was applied in the final implementation.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | It assumed timezone-naive values and did not account for the attendance-day shift boundary. | Test an overnight punch after midnight, or run with a non-IST server timezone. | Normalize instants to UTC, calculate against IST shift start, apply the strict 10-minute rule (≤10:00 → 0). |
| 2 | `compute_work_hours` | Binary-float rounding can disagree with the required half-up rounding (e.g. `8.425` rounds to `8.42` under banker's rounding). | Use an elapsed duration exactly halfway between two hundredths. | Compute with `Decimal` and `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | It always placed shift end on the attendance date and accepted any positive overtime. | Test an overnight shift or 29 vs. 30 overtime minutes. | Move overnight end to the next day, and require at least 30 whole minutes (≥30, not >0). |
| 4 | `health` | It reported healthy without checking MongoDB. | Stop MongoDB and request `/health`. | Ping MongoDB and return 503 when unavailable. |
| 5 | `create_employee` | A pre-insert duplicate check would race; it did not enforce the code format, date/time formats, or unequal shift times, and used a naive creation time. | Send concurrent duplicate creates, malformed input, or equal shift times. | Validate the contract with Pydantic, reject equal `shift_start`/`shift_end` with 422, store `created_at` as a UTC datetime, and rely on the unique `emp_code` index for races (catch `DuplicateKeyError` → 409). |
| 6 | `list_employees` | It skipped `page * page_size`, counted unfiltered employees, omitted the required stable sort, and returned `created_at` as a datetime rather than epoch milliseconds. | Request page 1, filter by department, or inspect the response type. | Use `(page - 1) * page_size`, a filtered `count_documents`, `emp_code` ascending sort, and `_dt_utc_to_ms` for serialization. |
| 7 | `punch_in` | Unknown employees caused a `KeyError`; milliseconds were interpreted in local time; date/late rules, input status validation, truncation, concurrency protection, and response serialization were missing. | Punch for an unknown employee, use a boundary/overnight timestamp, race requests, or inspect returned `punch_in` and `history`. | Validate employee (404), normalize/truncate epoch milliseconds, apply R1/R2, validate `status ∈ {PRESENT, WFH, ON_DUTY}`, rely on the unique `(emp_code, date)` index for races (DuplicateKeyError → 409), and return the contract shape. |
| 8 | `list_attendance` | It loaded and sorted the entire collection in Python (does not scale to ~100k records) and returned `_id` and timestamps in the wrong representation. | Run against a large collection or inspect response fields. | Filter, count, sort, skip, and limit in MongoDB using the `ix_date_emp` index; serialize only contract fields. |
| 9 | `punch_out` | It closed the first open record regardless of the punch-in time (broke overnight shifts across midnight), and had no atomic guard against concurrent punch-outs. | Punch out for an overnight shift, or send two simultaneous punch-outs. | Find the most recent record whose `punch_in ≤ punched_at` via the `ix_emp_punchin` index (works across midnight), then `findOneAndUpdate` with `punch_out: null` in the filter so the second concurrent punch-out gets 409. |
| 10 | `regularize` (PATCH) | Absent; corrections, audit history, derived-value recomputation and concurrency were not implemented. | Request any documented PATCH. | Implemented: validate the natural key, fetch employee (404) and record (404), enforce the ABSENT/LEAVE + punch-times rule (422), recompute R2-R5 from the final times, build `changes` only for fields that actually changed, append one history entry, and use `findOneAndUpdate` with an `$expr` history-length guard so concurrent edits return 409 to the loser instead of silently losing history. |
| 11 | Analytics endpoints | Absent; `employee_monthly`, `department_summary`, `late_leaderboard`, `department_trend` were not implemented. | Request any documented analytics route. | Implemented each as a MongoDB aggregation pipeline: `$facet` + `$group` for the employee summary; `$lookup` of `attendance_logs` from `employees` so people with no logs still count toward headcount; standard competition ranking computed in Python on top of the sorted aggregation output; `$densify` for one row per calendar day, with `$setWindowFields` for the 7-row moving average. |
| 12 | `explain` admin route | Absent. | Request `/admin/explain/<endpoint>` or check the plan for `COLLSCAN`. | Implemented `db.command('explain', …, verbosity='executionStats')` for both `find` (attendance_list) and aggregate pipelines (the four analytics endpoints). |
| 13 | Startup / indexes | No indexes were created, so uniqueness, the required list sort, and the analytics query plans were not met. | Concurrent writes or inspect `explain` on indexed routes. | Create idempotent unique and query-supporting indexes at startup via the FastAPI `lifespan` context. |

**Not defects:** The starter used `emp_code` as the employee key rather than MongoDB `_id`, and it stored calendar dates as strings; both match `DATA_MODEL.md`. Its `history` default shape was also right, although it was not yet used by a correction endpoint.
